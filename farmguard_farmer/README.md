# farmguard_farmer

Farmer-facing Flutter app for farm security monitoring.

## Camera pairing code UI

The Cameras tab generates the 6-digit code that links a new farm camera —
no curl needed. Entry points: a **Pair a camera** tonal button in the
Cameras tab's title row, and the same button in the "No cameras yet" empty
state. It opens a dialog (`lib/widgets/pairing_code_dialog.dart`) that:

1. Calls `POST /api/v1/pairing/code` (farmer token) and shows the code
   large with a live countdown (`Expires in mm:ss`).
2. Shows helper text mirroring the camera app's actual flow: *Open
   FarmGuard Camera on the farm phone → Start Monitoring → Pair this
   camera, then enter this code.*
3. Offers **Generate new code** at any time (codes are single-use, so
   regenerating is always safe); when the countdown hits zero the dialog
   flips to an expired state with the same affordance.
4. Errors inline: transient (network/timeout/5xx) → **Retry**; 401 → the
   dialog closes and the session-expiry path returns to login.

- Codes are **valid 5 minutes** (backend `CODE_TTL_MS`) and **single-use**:
  one redemption consumes the code; re-entering it later on the camera app
  fails with "not valid".
- The countdown clock is injectable (`PairingCodeDialog.now`) for tests;
  the API call is injected (`onCreateCode`) and fakes only — widget tests
  never touch a platform channel.

## Push notifications (Firebase Cloud Messaging)

Stage 7 client wiring: the app receives FCM pushes for **LIVE** detections and
routes notification taps to the matching `DetectionDetailScreen`.

### Firebase project & app

- Firebase project: `project1-eaebc` (real project; do not create others).
- Android app registered via FlutterFire CLI:
  package name `com.example.farmguard_farmer`,
  app id `1:342457185184:android:269863db7a5b5d7c1d6ac5`.
- Config is **Dart-only**: `lib/firebase_options.dart` (generated by
  `flutterfire configure`) + `Firebase.initializeApp` inside
  `FirebaseMessagingGateway`. No google-services Gradle plugin is applied —
  the generated `android/app/google-services.json` is inert/unread without
  it and may be ignored.
- Packages: `firebase_core ^5.2.0`, `firebase_messaging ^17.1.0`
  (installed with `flutterfire_cli 1.5.0`).
- `android/app/src/main/AndroidManifest.xml` declares
  `android.permission.POST_NOTIFICATIONS` (required on Android 13+).

### Client flow

- `MessagingGateway` (`lib/services/messaging/messaging_gateway.dart`) is the
  injectable seam: `initializeAndRequestPermission`, `getToken`,
  `tokenRefresh`, `taps`. Production implementation
  `FirebaseMessagingGateway` is constructed only in `AppServices.production`;
  tests inject `FakeMessagingGateway` (widget tests hang forever on
  unmocked platform channels, so no Firebase code runs in tests).
- After successful auth (login/register or bootstrap with a valid stored
  token), `AuthGate` starts a `PushSession`
  (`lib/services/messaging/push_session.dart`):
  1. Firebase init + background-isolate handler registration.
  2. Permission prompt. **Declined → registration skipped silently; the app
     remains fully functional** (no push, no crash).
  3. Token → `NotificationRepository.registerDevice(token, platform:'android')`
     → `POST /api/v1/notifications/register-device` (`{fcm_token, platform}`).
  4. `tokenRefresh` stream → re-register on every rotated token.
- Logout (Settings → Account) unregisters the device token
  (`DELETE /api/v1/notifications/unregister-device`) **before** the session
  is cleared — best-effort; logout never fails because unregister did.
- Session expiry (401) tears the push session down the same way.

### Tap routing

- Taps (background resumption via `onMessageOpenedApp`, and cold start via
  `getInitialMessage`, buffered until the first listener) are delivered
  through one `taps` stream; `MainShell` subscribes.
- `event_id` present → `EventRepository.getEvent(eventId)` → push
  `DetectionDetailScreen`. Event deleted/unknown (404) → snackbar
  "Event no longer available", no navigation. Taps without `event_id` →
  no-op. 401 → session-expiry path.
- In-foreground messages are intentionally ignored (minimal scope); the
  system tray shows them when backgrounded. Foreground display +
  data-only background handling are future enhancements (the registered
  `firebaseMessagingBackgroundHandler` is a documented no-op).

### Server-side service account (NOT done)

The backend Worker needs a Firebase service-account private key JSON as the
`FCM_SERVICE_ACCOUNT` secret to send pushes. `gcloud` is not installed on
this machine, so the key was **not** generated. Manual steps:

1. Open the Firebase console → project **project1-eaebc**.
2. ⚙️ Project settings → **Service accounts** tab.
3. Select **Firebase Admin SDK** → **Generate new private key** → confirm.
4. Save the downloaded JSON **locally only** (never commit it), e.g.
   `~/.secrets/farmguard-fcm-service-account.json`.
5. Upload it as the Worker secret:
   `cd farmguard-backend && wrangler secret put FCM_SERVICE_ACCOUNT < ~/.secrets/farmguard-fcm-service-account.json`

(If the default service account is missing in the console: IAM → find
`firebase-adminsdk-*@project1-eaebc.iam.gserviceaccount.com` → Keys →
Add key → JSON.)
